# 마음콩 — 학생·교사 통합 프로토타입

첨부된 디자인을 기준으로 구현한 **React + TypeScript + Vite + Tailwind + Supabase** 프로젝트입니다.
학생 화면 `/student`와 교사 화면 `/teacher`가 동일한 Supabase 프로젝트를 이용합니다. 로그인 이후 화면과 접근 권한은 URL이 아니라 서버에 저장된 사용자 역할을 따릅니다.

> **현재 상태: 연결 준비된 실행 소스. 실제 Supabase 프로젝트 연결·배포는 수행하지 않았습니다.**
> 연결 정보가 없으면 로그인 화면에 ‘서버 연결 전’을 표시하고 가입/로그인을 비활성화합니다. 임의 학생·교사 데이터나 가짜 연결 성공을 보여 주지 않습니다. 실제 운영 서비스가 아니라 파일럿 준비용 프로토타입입니다.

## 1. 시작하기

Node.js 22 LTS와 npm을 준비하고 이 폴더에서 실행합니다.

```sh
npm ci
cp .env.example .env
# .env 두 값을 자신의 Supabase 프로젝트 값으로 변경
npm run dev
```

Windows PowerShell에서는 `Copy-Item .env.example .env`를 사용합니다. 터미널에 출력되는 주소로 접속합니다.
`.env`를 설정/변경한 뒤에는 Vite를 재시작하세요. HTML 파일을 더블클릭하는 방식으로 실행하는 프로젝트가 아닙니다.

```env
VITE_SUPABASE_URL=https://실제프로젝트.supabase.co
VITE_SUPABASE_ANON_KEY=실제_공개_anon_또는_publishable_키
```

**service_role / secret 키, DB 비밀번호는 절대로 입력하지 마세요.** VITE_ 환경변수는 브라우저에 공개됩니다. 이 프로젝트는 공개 클라이언트 키와 RLS를 전제로 합니다.

## 2. Supabase 설정 순서

1. 테스트용 새 Supabase 프로젝트를 만듭니다. 학교 실데이터를 처음부터 넣지 마세요.
2. SQL Editor에서 `supabase/001_schema.sql`을 **한 번** 실행합니다. 새 DB용 초기 마이그레이션이며 반복 실행용이 아닙니다.
3. `supabase/002_questions.sql`을 실행합니다. 질문 데이터는 실제 운영 가능한 초기 콘텐츠이며 학생 응답 테스트 데이터가 아닙니다.
4. Auth > URL Configuration에서 Site URL 및 허용 Redirect URL에 개발 주소와 배포 주소를 등록합니다. 비밀번호 재설정도 이 주소로 돌아옵니다.
5. Auth > Providers에서 이메일 로그인을 켜고 이메일 확인 정책을 정합니다. 메일 발송 제한 및 SMTP 설정을 확인합니다.
6. Realtime에서 `mood_records`, `counseling_requests`, `water_transactions`, `bean_inventory`, `notifications`, `sharing_preferences`, `classroom_members`, `reward_inventory`가 publication에 포함되어 있는지 확인합니다. 초기 SQL이 이를 추가합니다.
7. 공개 URL과 공개 키를 `.env`에 설정하고 앱을 실행합니다.

DB SQL을 수동으로 변경했다면 테스트 결과는 그 변경본까지 보증하지 않습니다. 기존 public 스키마에 다른 서비스가 있는 프로젝트에서는 이 초기 SQL을 적용하지 마세요. 함수·테이블 권한을 일괄 초기화하므로 **전용 새 프로젝트**를 전제로 합니다.

## 3. 테스트 계정 만들기

미리 만들어 둔 계정·공통 비밀번호는 없습니다. 실제 Auth 계정을 사용합니다.

### 교사 A
1. `/teacher`에서 교사용 회원가입 → 이메일 인증 → 로그인합니다.
2. 운영자가 신원과 학교 권한을 확인한 후 SQL Editor에서 승인합니다.

```sql
select id,nickname,organization from public.profiles where role='teacher';
-- 조회한 실제 UUID로 대체합니다.
update public.profiles
set approved=true
where id='교사_A의_실제_UUID' and role='teacher';
```

3. 앱에서 승인 상태를 확인하고 ‘설정 → 새 학급 만들기’로 학급을 생성합니다.
4. 자동 생성된 12자리 코드를 학생에게 전달합니다.

### 학생 A
1. 별도 브라우저/시크릿 창 또는 다른 기기에서 `/student`로 회원가입·로그인합니다.
2. 콩을 선택합니다. ‘내 정보 → 우리 반 연결’에 교사 A의 코드를 입력합니다.
3. 학교의 실제 안내·필요한 동의 절차를 진행한 뒤 공유 설정을 켭니다. **UI 체크는 법적 동의 수집 시스템을 대신하지 않습니다.**
4. 오늘 질문에 답하고 ‘선생님과 공유’ 여부를 확인하여 저장합니다.
5. 교사 A의 학생 관리에서 학생 A를 선택하면 허용된 기록이 조회됩니다.

교사 B / 학생 B도 다른 이메일로 만들고 별도 학급에 연결하면 학급 간 접근 차단을 확인할 수 있습니다. 같은 브라우저 탭에서는 Supabase 세션이 공유될 수 있으니 교사/학생 테스트에는 브라우저 프로필을 구분하세요.

## 4. 구성

```text
src/main.tsx               역할별 인증·학생 UI·교사 UI·실제 DB 조회/RPC·Realtime
src/domain.mjs             한국시간 날짜, 질문 선택, 성장 단계, 범주별 집계
src/style.css              참고 이미지 기반 반응형 스타일 + Tailwind
public/assets/*.png        첨부 디자인에서 추출한 콩 캐릭터 원본 조각
public/questions.json      테스트용 질문 목록 복제본 (서비스는 DB에서 질문 조회)
supabase/001_schema.sql    테이블·RLS·검증된 서버 RPC·Realtime publication
supabase/002_questions.sql 초기 질문 콘텐츠
supabase/003_operations.sql 운영자 승인·보관·삭제 관련 SQL 참고
supabase/004_integration_check.sql 연결 후 RLS·학급 연동 점검 SQL
scripts/                   없음 (setup_project.py는 초기 파일 생성용, 재실행 불필요)
tests/*.test.mjs            도메인 및 PostgreSQL 엔진 기반 보안·거래 테스트
TEST_REPORT.md             실제 수행 범위 / 미수행 범위
ACCEPTANCE.md              실서비스 연결 후 인수 테스트 절차
```

학생·교사 UI는 한 프론트엔드 코드베이스 내에서 분리된 화면입니다. 두 개의 독립적인 배포가 필요하면 같은 소스를 두 사이트에 배포해도 되며, 두 사이트에 같은 Supabase URL·공개 키를 사용합니다. 관리자용 웹 UI는 포함하지 않고 운영 SQL 경로로 구분합니다.

## 5. 구현된 주요 동작

### 학생
- 이메일 가입·로그인·로그아웃·재설정 메일 및 새 비밀번호 설정
- 학급 코드 연결, 캐릭터 5종 선택, 물방울 소모와 성장, 완료 후 새 콩 선택
- 한국 날짜별 기본 질문 1개, 요일별 유형, 일요일 고정 문구
- 기본 질문과 테마 질문 저장·수정, 비공개 자유 일기
- 일일 기본 +1 및 테마별 하루 한 번 +1~+5, 중복 지급 차단
- 기본 공유 설정 및 답변 단위 공유 선택, 기본 공유 철회 시 교사 조회 차단
- 7일·30일 표현 타임라인과 범주별 선택 빈도 차트 (감정 점수 없음)
- 서버 추첨 룰렛, 테스트 기프티콘/화분 보유 및 테스트 사용 처리
- 친구 초대 링크, 학급 연결된 가입 7일 이내 계정의 1회 인증 보상
- 상담 요청·수정/추가 내용·취소·진행 상태 확인
- 물방울 내역, 과거 성장 콩 도감, 계정·데이터 삭제 요청 접수

### 교사
- 승인 대기/승인 후 접근, 복수 학급 생성과 전환, 학급 코드 조회
- 연결 학생 목록, 공유된 학생별 날짜 기록, 7일·30일 차트
- 오늘 공유 기록 참여 인원·비율, 범주별 집계, 날짜별 공유 참여 차트
- 상담 요청 전달 및 상태/후속 확인 관리, 교사용 비공개 메모
- 학생의 직접 요청, 7일간 확인 가능한 공유 기록 부재, 최근 신호등 3회의 ‘멈추고 싶음’ 표현에 대한 근거 표시

### 서버
- 모든 테이블 RLS. 클라이언트의 테이블 직접 변경 권한 제거
- 물방울·성장·룰렛·보상 지급은 security definer RPC로 처리
- 학생 프로필 행 잠금으로 같은 학생의 보상/소비 연산 직렬화
- 기본/테마 일별 고유 인덱스 및 거래 참조 고유 제약
- 기본 공유 철회, 비공개 일기 및 교사용 메모의 RLS 격리
- 핵심 변경과 학생 상세 조회 감사 기록
- Realtime 변경 구독 + 30초 재조회 + 화면 재활성화 시 재조회

교사 화면의 참여율은 **공유된 기본 기록 수 / 전체 연결 학생 수**입니다. 비공개 학생의 작성 여부를 우회적으로 공개하지 않으므로 실제 작성률과 다를 수 있습니다. 무기록은 문제나 위험의 근거로 확정하지 않습니다.

## 6. 디자인 적용 범위

첨부 파일의 흰색 배경, 연두색 주요 카드(`#a8c9a3`), 연한 초록(`#eaf3e7`), 진한 초록 글자(`#25382d`), 하늘색 보조 카드(`#e3eef5`), 큰 모서리와 콩 이미지를 반영했습니다. 학생 화면은 최대 473px 폭을 유지하고 교사 화면은 반응형 대시보드로 구분합니다.

**스크린샷과 픽셀 단위로 동일하다고 보증하지 않습니다.** 원본 폰트/캐릭터 개별 원화가 없으므로 기본 한글 폰트와 스크린샷에서 잘라낸 콩 이미지를 사용합니다. 미세한 배경색 조각이 남을 수 있습니다. 하단 메뉴는 최종 요청에 맞춰 5개로 변경했습니다. 참고 이미지의 감정 점수 선 그래프는 최종 요구의 ‘감정 점수화 금지’에 따라 범주형 타임라인과 빈도 차트로 교체했습니다.

## 7. 실행·빌드·배포

```sh
npm test
npm run build
npm run preview
```

배포 서비스의 빌드 명령은 `npm ci && npm run build`, 결과 디렉터리는 `dist`입니다. 환경변수 두 개는 **빌드 시점**에 입력해야 합니다. Vercel용 `vercel.json`과 Netlify용 `public/_redirects`를 포함합니다. 다른 정적 호스팅도 `/student`와 `/teacher` 요청을 `/index.html`로 연결하는 SPA fallback이 필요합니다.

배포 후 HTTPS 주소를 Supabase Auth의 허용 Redirect URL에 추가하고 휴대폰/PC에서 테스트합니다. 배포 도메인이 없으므로 이 패키지에는 실제 접속 URL이 없습니다. 이미 빌드한 dist는 연결 정보 없는 화면이며 실제 운영 배포 전에는 반드시 자신의 환경변수로 재빌드하세요.

## 8. 보안·운영상 반드시 보완할 부분

- 학교별 개인정보 처리방침, 보호자·학생 안내/동의 증빙, 수집 최소화, 보관/폐기 정책 확정
- 교사 신원 확인·학교 담당자 승인 프로세스, MFA 및 세션 정책, 계정 복구 통제
- 삭제 요청은 접수만 구현. 실제 삭제는 담당 운영자가 Auth 사용자 및 연관 DB/백업 보관 범위를 검토 후 처리
- 보관기간은 설정값/점검 SQL을 제공하며 자동 만료 삭제 배치는 미연결
- 학급 이동·교사 교체 시 과거 기록과 상담 정보의 귀속 정책. 현재 단순 연결 변경 시 과거 공유 기록 접근이 새 담당 교사에게 이어질 수 있으므로 수동 이전 절차 필요
- 관리자 전용 웹 UI, 운영자 변경 감사, 메모의 별도 키 암호화/키 관리, 전체 조회 감사 확대
- 실제 기프티콘 API·재고·실패 재시도·중복 발행 방지 외부 연계. 현재 모든 보상은 테스트 전용
- 꾸미기 화분은 지급/보유만 구현. 콩 장착·다양한 아이템 효과는 미구현
- 성장 단계는 수치/단계명/보조 아이콘으로 변화. 단계별 새로운 콩 원화 25종 및 고유 성장 캐릭터 애니메이션은 미제공
- 친구 초대는 서버 1회 제약을 적용했으나 실제 인물 단위 중복 계정·다계정 악용 방지와 관리자 취소 기능은 후속 과제
- 푸시/이메일 상담 알림은 미연결. 현재 알림 테이블+앱 내 상담 목록 Realtime 갱신으로 확인
- 학생이 직접 만드는 개별 관심 신호 규칙, 통계 익명화 최소 인원 기준, 학생명 검색/대량 내보내기, 운영자 질문 관리 화면은 후속 과제
- 질문은 초기 33개(기본 25개+테마 8개)이며 비일요일 유형별 4개를 순환합니다. 무한 생성/AI 분석은 없습니다.
- 감정 자동 진단·위험도 확정·개인별 순위는 구현하지 않았습니다.
- 실제 Supabase Auth / SMTP / Realtime / 기기별 반응형 / 장기 세션 유지 / 동시성 부하의 통합 검증은 연결 후 필요
- 초기 조회는 Supabase 기본 페이지 제한(일반적으로 1,000행)을 따릅니다. 실제 장기 운영 전 기간 기반 쿼리·페이지네이션·서버 집계를 적용해야 합니다.
- RLS만으로 접근 정당성이 완성되지는 않습니다. 운영자 계정·백업·로그에도 동일한 보호 정책 필요

실제 학생 데이터를 투입하기 전 반드시 테스트 계정으로 인수 테스트를 끝내고 보안·개인정보 검토를 거치세요.
